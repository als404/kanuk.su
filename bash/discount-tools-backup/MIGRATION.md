# Перенос сайта и резервного копирования на другой хостинг

Инструкция для Linux VPS с SSH/root. Для обычного shared hosting сначала проверьте доступность Bash, cron, mysql/mysqldump, curl FTP и необходимых прав. Команды ниже - шаблоны; пути, база и сервисы нового сервера определяются его панелью и окружением.

## 1. Подготовить перенос

- Зафиксировать версию CMS, PHP и расширения, MySQL/MariaDB, кодировку, веб-сервер, document root, владельца файлов и часовой пояс.
- Проверить совместимость старого Bitrix с новым PHP и БД на тестовом экземпляре. Не совмещать переезд с неподготовленным обновлением CMS/PHP.
- Сохранить отдельно настройки nginx/Apache/PHP, cron всех пользователей и панели, DNS, SSL, почтовые настройки, msmtp, внешние интеграции и правила доступа.
- Проверить интеграции 1С/Bitrix24, IP-ограничения, пути обмена и импортов, лицензии и исходящие подключения с нового IP.
- На время финальной копии остановить запись заказов/обменов или включить согласованный режим обслуживания. Это снижает расхождение файлов и БД.
- Не удалять старый хостинг до проверки сайта, обменов, почты и нового ночного backup.

## 2. Получить финальную резервную копию

На старом сервере:

```bash
/home/script/backup.sh --all
tail -n 60 /home/script/logs/backup_v2.log
```

Убедиться в `tar_exit=0`, `curl_exit=0`, `FTP UPLOAD OK`, `SUCCESS` и отсутствии `.part` у выбранного архива. Скачать его на защищённый компьютер или новый сервер. Оставить независимую копию вне каталога, где работает ротация.

Проверить скачанный файл:

```bash
gzip -t /secure/path/backup.tar.gz
tar -tzf /secure/path/backup.tar.gz > /secure/path/backup-contents.txt
```

Проверить наличие `.htaccess`, файлов сайта, `__backup/<DB_NAME>.sql.gz`, `__backup/backup-info.txt`. Для контрольной суммы используйте `sha256sum` после скачивания и сравнивайте её при дальнейших переносах файла. Она не доказывает корректность исходной базы; нужен тест восстановления.

## 3. Подготовить новый сервер

Установить совместимое окружение сайта, создать отдельную БД и пользователя. Установить зависимости backup: Bash, tar, gzip, coreutils, awk, util-linux, curl с FTP, совместимые mysql/mysqldump и msmtp. Названия пакетов зависят от ОС. Если клиент mysqldump переименован в mariadb-dump, обеспечить совместимый вызов или адаптировать скрипт.

Создать FTP-каталог и проверить квоту: место нужно как минимум для 10 архивов и одного нового временного архива. Для теста использовать отдельный FTP-каталог: `--all` запускает ротацию автоматически. Два сервера с одинаковыми префиксом и FTP-каталогом могут удалять архивы друг друга; локальный flock не защищает между серверами.

## 4. Восстановить файлы и БД

Сначала распаковать доверенный архив в отдельный закрытый каталог вне document root:

```bash
mkdir -p /secure/restore-stage
tar -xzf /secure/path/backup.tar.gz -C /secure/restore-stage
gzip -t /secure/restore-stage/__backup/OLD_DATABASE.sql.gz
```

Имя `OLD_DATABASE` заменить именем дампа из списка архива. Перенести файлы сайта из staging в новый document root, сохраняя скрытые файлы, но не копируя `__backup` в публичный каталог. Установить владельца и права по требованиям нового хостинга; не применять `chmod 777` ко всему сайту.

Импортировать дамп в заранее созданную пустую БД. Пароль не указывать в командной строке; использовать защищённый клиентский конфиг или стандартный безопасный механизм нового сервера. Пример с интерактивным запросом пароля и временным SQL вне веб-корня:

```bash
umask 077
gzip -dc /secure/restore-stage/__backup/OLD_DATABASE.sql.gz > /secure/restore-stage/database.sql
mysql -h localhost -u NEW_DB_USER -p NEW_DB_NAME < /secure/restore-stage/database.sql
```

После успешной проверки удалить временный несжатый SQL. Обновить реквизиты БД в настройках CMS (для Bitrix проверить `bitrix/.settings.php` и `bitrix/php_interface/dbconn.php`, если используются). Проверить абсолютные пути, права на upload/кэш и URL. Исключённые кэши будут созданы заново сайтом при корректных правах. `__backup` не оставлять доступным через HTTP.

## 5. Настроить backup на новом сервере

Установить файлы по README. Рабочий `backup.conf` и `.msmtprc` передать отдельно защищённым способом, без Git. Актуализировать:

| Где | Что проверить |
| --- | --- |
| backup.conf | DIR_SITE, DIR_BACKUP, DB_HOST/USER/PASS/NAME, FTP_IP/USER/PASS/DIR |
| Начало backup.sh | CONFIG, LOG_FILE, LOCK_FILE, MIN_FREE_MB, BACKUP_PREFIX |
| Начало backup.sh | EMAIL_TO/FROM, MSMTP, MSMTP_CONFIG, MSMTP_ACCOUNT, MAIL_ON_SUCCESS |
| Сервер/панель | cron, часовой пояс, права, доступы к БД/FTP/SMTP, квота FTP |

Если меняется document root, каталог локальных backup держать вне него. Не переносить старый рабочий каталог `.backup_v2_work` и временные credential-файлы.

```bash
chmod 700 /home/script/backup.sh
chmod 600 /home/script/inc/backup.conf
bash -n /home/script/backup.sh
/home/script/backup.sh --check
/home/script/backup.sh --test-email
/home/script/backup.sh --all
tail -n 60 /home/script/logs/backup_v2.log
```

Первый полный запуск делать в отдельный тестовый FTP-каталог. Скачать созданную копию и проверить восстановление файлов и БД в изолированном окружении. Затем настроить рабочий FTP-каталог и согласованную политику хранения. Для новой независимой серии использовать отдельный префикс или каталог.

## 6. Проверить сайт до DNS-переключения

Открыть сайт на новом сервере через локальный hosts или иной тестовый маршрут с правильным доменом. Проверить каталог, изображения, поиск, корзину, тестовый заказ, админку, HTTPS, редиректы, отправку почты и ошибки PHP. Не включать реальные обмены, рассылки и агенты на двух экземплярах одновременно.

Перед переключением синхронизировать изменения, появившиеся после финального снимка, либо сохранять запрет записи до завершения переноса. Переключить нужные DNS-записи и SSL по фактической сетевой схеме, учитывая reverse proxy/CDN и локальные DNS. Если почта не переезжает, не менять MX без отдельной необходимости.

## 7. Переключить задания

Отключить backup и задачи сайта на старом сервере, затем включить соответствующие задачи на новом. Добавить пример cron из пакета в root crontab, проверить отсутствие дублей в панели и других crontab. Проверить фактический часовой пояс и не пересекать backup с тяжёлыми импортами/обновлениями.

После первого ночного запуска проверить свежие `STREAM RESULT`, `FTP UPLOAD OK`, `FTP RETENTION OK`, `SUCCESS`, доступность новой копии и уведомлений. Контролировать объём диска и логи. Проверить отдельно перенос скрипта очистки кэша и мониторинга синхронизации, если они используются: в данный пакет они не входят.

## 8. Откат

Если ошибка только в backup, отключить новое задание cron и вернуть предыдущие скрипт/конфигурацию из сохранённой копии, затем проверить синтаксис и ручной запуск.

Если требуется откат сайта, сначала остановить запись на новом сервере и сохранить его актуальные данные. Не возвращать DNS на старую копию без плана переноса новых заказов и изменений: они иначе потеряются. Восстановить согласованное состояние, вернуть маршрут/DNS и включить фоновые задания только на одном активном сервере. Старые архивы и исходный сервер сохранять до принятия переноса.
