# Установка и перенос — DT Discontinued Products 1.0.0

## 1. Подготовка

Работать сначала на тестовой копии. Проверить версию Битрикс/PHP, шаблон elektro_flat, наличие Altop и зависимых доработок dt.catalogproperties, dt.documents и дилерского меню. Сделать резервную копию БД и всех файлов из MANIFEST.txt; для новых файлов зафиксировать их отсутствие до установки. Проверить права владельца сайта и ACL. Не копировать кэш и production-секреты. PHP использует короткие теги: `short_open_tag=1`.

При полном переносе сайта вместе с БД числовые ID обычно сохраняются, но их необходимо проверить. При новой БД создать свойство через административную панель в инфоблоке товаров: `DISCONTINUED`, список с отображением флажком, одиночное, необязательное, без значения по умолчанию, единственное значение с XML_ID `Y`. Проверить соответствие ID инфоблока в `DTDiscontinuedProduct::PRODUCT_IBLOCK_ID` (16 в исходной БД) и других параметрах шаблонов. ID 692 и 79 относятся к исходной базе; не навязывать их новой базе. Проверить связку SKU, если она используется на целевом сайте.

## 2. Перенос исходников

`files/` содержит снимки файлов сайта, а не патчи. Сравнить каждый файл с целевым исходником (`diff -u` или VSCode Compare). Не использовать массовый cp/rsync поверх production. При совпадающей базе переносить только согласованные изменения. При различиях объединять вручную, сохраняя постороннюю логику.

1. Создать `local/php_interface/dt_discontinued.php`, если отсутствует.
2. В существующий `bitrix/php_interface/init.php` внутри PHP-блока добавить содержимое `integration/init.discontinued.php.txt` один раз. Не дублировать события; не заменять весь init.php. Убедиться, что Битрикс загружает именно этот init.php.
3. В `catalog/index.php`, комплексных element.php/section.php и `ajax/fast_wiu.php` перенести передачу DISCONTINUED. Сохранить параметры и сторонние интеграции.
4. Слить изменения соответствующих шаблонов из MANIFEST.txt (детальная, быстрый просмотр, плитка, filtered, bigdata, сравнение, полный поиск). Перенести полный локальный шаблон `altop/search.title/.default/` включая скрытые файлы и языковые ресурсы, если локальный шаблон отсутствует; иначе сравнить и объединить. Проверить, что компонент выбирает именно локальный шаблон.
5. Добавить новые защищённые endpoints в `/ajax/` и согласовать изменения `ajax/add2basket.php` с клиентскими обработчиками семи компонентов. Не заменять только сервер или только клиент: JSON-контракт должен совпадать.
6. Добавить `integration/quantity-limit.js` и `integration/discontinued.css` в существующие глобальные script.js и custom.css соответственно, если блоков ещё нет. Сохранить прочие изменения.
7. Проверить синтаксис PHP и JS; применить на тестовой копии; проверить фактическую регистрацию событий и сценарии TESTING.md. После резервирования согласованных файлов применить на production и выполнить выборочную инвалидацию нужного кэша.

Пример проверки PHP на исходном сервере:

```bash
cd /var/www/discount-tools/public || exit 1
while IFS= read -r F; do
  case "$F" in *.php) php74 -d short_open_tag=1 -l "$F" || exit 1;; esac
done < /path/to/MANIFEST.txt
```

На Mac для локальной проверки: `shasum -a 256 -c SHA256SUMS.txt`. Использовать VSCode для исходников; для конфигурации сервера — SSH и vi/vim.

## 3. Смена хостинга или домена

Проверить DOCUMENT_ROOT, PHP-FPM, SITE_ID/SITE_DIR, SSL, владельца файлов, активный шаблон и параметры Битрикс. AJAX-адреса формируются относительно SITE_DIR/корня сайта; проверить POST и текущий сеанс. Не открывать Nginx-доступ к `.default` ради popup: запросы идут через `/ajax/search_title_popup.php` и `/ajax/catalog_compare_popup.php`. GET к этим endpoint должен возвращать 405. Сохранить штатный секрет подписи Битрикс при переносе или обеспечить обновление старых сеансов; не публиковать секреты.

Для действующего cost_update проверить `config.php`: document_root, iblock_id, html_cache_domain, catalog_path, site_id. При смене домена изменить html_cache_domain на фактический домен композитного кэша. Проверить cron, лог, права и очередь pending_cache.json. Не включать credentials поставщиков в Git. cost_update не входит в эту разработку и при внедрении DISCONTINUED не изменялся.

## 4. Историческая миграция 29 товаров — не установщик

Скрипты `scripts/migrate_discontinued.php` и `scripts/apply_discontinued.php` сохранены без изменения. Они предназначены исключительно для проверенного набора исходной базы за 25.11.2026. В комплекте намеренно отсутствуют `products_before_migration.ser` и `migration_plan.ser`; скрипты без них не выполнят миграцию. Оригиналы находятся в защищённом серверном бэкапе `/home/als/backups/discontinued_20261124_140225/migration_20261125_175425`.

Первый скрипт читает исходный снимок, проверяет SHA-256, очищает старые текстовые статусы, проверяет сохранение защищённого содержимого и пишет план. В БД не пишет. Второй проверяет обе контрольные суммы, 29 записей, идентичность товаров, свойство 692/инфоблок 16 и единственный XML_ID Y; использует фиксированный DOCUMENT_ROOT. Режимы `--check` (только исходное состояние), `--apply` (запись), `--verify` (только итоговое состояние), `--rollback` (восстановление описаний и свойства). Весь набор не обёрнут в единую транзакцию. Rollback на production практически не проверялся. Некоторые ошибки исторических скриптов возвращают текстовый exit без ненулевого кода; оценивать также сообщения SUCCESS/ERROR.

**На действующем сайте миграция уже выполнена. Повторно не запускать --apply.** При переносе полной БД повторная миграция не нужна. При новой базе провести новый поиск старых статусов, ручную проверку описаний, сформировать новый снимок и план с актуальными ID и контрольными суммами. Не отключать проверки хэшей ради запуска старого скрипта. Сначала испытать процедуру и восстановление на тестовой копии.

## 5. Откат кода

Восстановить исходные версии изменённых файлов из предустановочного бэкапа или откатить только соответствующие блоки в общих файлах, удалить только созданные этой установкой endpoints/шаблоны, если они не используются другими функциями. Удалить регистрацию событий и очистить целевой кэш. Изменение данных отдельно согласовать: удаление свойства или откат описаний может уничтожить последующие изменения. Не удалять свойство автоматически при откате кода. Проверить обычный каталог, корзину и заказ после отката.
