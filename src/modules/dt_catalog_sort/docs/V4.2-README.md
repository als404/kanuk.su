# Автообновление индекса сортировки — V4.2, тест 247

**Только test:** `discount-tools-test`, Bitrix 17.5.8, PHP 7.4, товары в инфоблоке 16, SKU в 17, привязка 72, сайт `s1`, цена для группы 2 без купонов. Production не изменять. Эта версия **дополняет**, а не заменяет имеющийся V3 `dt_catalog_sort.php` и рабочий `section.php`.

## Задача

На тесте уже заполнены `DT_SORT_GROUP` (692), `DT_SORT_PRICE` (693), `DT_SORT_ZERO` (проверено у 6074 товаров). Режимы сортировки работают, но после изменения цены свойства сохраняют старые значения. V4 делает:

1. **События:** цена/товар/свойства → постановка ID товара в очередь, без расчёта во время веб-запроса.
2. **CLI worker:** пересчёт по актуальным скидкам и запись **только при отличии**, затем удаление ID из очереди (с защитой `VERSION` от потери повторного события).
3. **Периодическая сверка:** каждый запуск обходит следующую часть каталога; в конце начинает с начала. Покрывает сроки действия скидок, импорт или изменение данных, пропущенные событиями. Задержка полной сверки зависит от числа товаров и размера партии, для 6074 товаров и 300/мин — примерно 21 мин, плюс время выполнения cron. Это не мгновенное обновление скидок по расписанию.
4. **Кеш:** после реальных изменений свойств сбрасывается управляемый кеш по тегу `iblock_id_16`. Композитный HTML-кеш отдельно не удаляется; его поведение проверить в браузере.

Код не меняет базовые цены, правила скидок, остатки, старые `MINIMUM_PRICE`, `rating`, `CATALOG_SORT_PRIORITY` и ядро Битрикс. Создаёт **две собственные таблицы** для очереди и курсора: `dt_catalog_sort_queue`, `dt_catalog_sort_state`.

## 1. Диагностика и первичный preview (без записей)

```bash
PHP=/opt/remi/php74/root/usr/bin/php
TOOL=/var/www/discount-tools/tools/dt_catalog_sort_auto.php
LIB=/var/www/discount-tools/public/local/php_interface/dt_catalog_sort
$PHP -l "$LIB/DtCatalogSortAuto.php"
$PHP -l "$LIB/hooks.php"
$PHP -l "$TOOL"
$PHP "$TOOL" --find --article=2100089 --brand=BREXIT
```

**Важно:** `2100089` — **артикул**. При предыдущей диагностике он соответствовал внутреннему ID **5238**. Проверяйте через `--find` повторно после синхронизации каталога. Команда `--find` ищет товар по точному значению свойства `ARTNUMBER` и сверяет производителя по свойству `MANUFACTURER`, не используя `NAME` как критерий. Подставить фактический ID ниже. В карточке товара может показываться артикул из отдельного свойства.

```bash
ID=<реальный_ID_из_результата>
$PHP "$TOOL" --preview --ids="$ID"
```

Если цена в карточке сейчас 1000 ₽, ожидаем `PRICE=1000.00, ZERO=0, GROUP=10` и `STATUS=WOULD_UPDATE`, если индекс ещё старый. При иной цене сверять фактические данные. `--preview` не изменяет БД.

### Проверка точного поиска (изменение V4.1)

`--find` требует **оба** параметра: `--article` и `--brand`. Сначала выполняется фильтрация по `ARTNUMBER`, затем точная (без учета регистра) проверка `MANUFACTURER`. Если свойство производителя хранит ссылку на элемент бренда, сравниваются имя и код связанного элемента; для строк и списков сравниваются текстовые значения. Поиск **не ищет часть названия товара** и **никогда не подставляет первый результат автоматически**.

Пример: `2100089 / BREXIT` → ожидается `RESULT=UNIQUE ID=5238`, если фактические свойства на сервере соответствуют диагностике. При `RESULT=NOT_FOUND` посмотрите `SKIP ... MANUFACTURER=...` и проверьте тип/значение свойства. При `RESULT=AMBIGUOUS` выберите правильный ID вручную; запись не выполняется.

**Важно:** автоматическое обновление из событий Битрикс использует внутренний ID товара напрямую. Поиск по артикулу/бренду нужен только оператору для диагностического выбора товара и не участвует в событии обновления цены.

## 2. Создание собственных таблиц и тест очереди

Перед `--install` убедиться в актуальности резервной копии тестовой БД. В отличие от пользовательских цен это создание только **служебных таблиц**. Запись защищена по hostname.

```bash
$PHP "$TOOL" --install --apply --confirm=test
$PHP "$TOOL" --status
$PHP "$TOOL" --enqueue --ids="$ID" --apply --confirm=test
$PHP "$TOOL" --status
$PHP "$TOOL" --run --queue=20 --sweep=0 --apply --confirm=test
$PHP "$TOOL" --preview --ids="$ID"
$PHP "$TOOL" --status
```

Ожидаем `ENQUEUED`, далее `QUEUE ... changed=1` (если индекс отставал), затем `STATUS=UNCHANGED`, `queued=0`. Если `changed=0`, цена могла быть уже пересчитана вручную.

`--recalc --ids="$ID" --apply --confirm=test` — аварийное адресное обновление без очереди. **Не использовать до проверки preview**.

## 3. Регистрация событий (только после успешного теста очереди)

1. Сделать копию `local/php_interface/init.php` вне публичного сайта.
2. Через VSCode добавить строки `deploy/init.snippet.php` в существующий `init.php`, сохраняя кодировку. Защита: `gethostname() === 'discount-tools-test'`.
3. Выполнить `$PHP -l /var/www/discount-tools/public/local/php_interface/init.php`.
4. Через административную карточку тестового товара изменить цену **только на test 247**, затем проверить очередь `$PHP "$TOOL" --status`. При изменении должны появиться записи `queued>0`. Если очередь пуста, нельзя утверждать, что автоматическое событие сработало: нужно определить, какое событие реально генерирует установленная версия каталога.
5. Запустить `$PHP "$TOOL" --run --queue=20 --sweep=0 --apply --confirm=test`, затем `--preview` и проверить отображение на странице каталога. Для проверки скидок — изменить тестовую скидку, проверить обновление курсора либо выполнить `--restart-sweep` (сброс курсора только на тесте).

**Важно:** в старых версиях обработчик `OnPriceUpdate` может быть отключён, поэтому зарегистрированы несколько вариантов D7 и legacy. Регистрация сама по себе не является доказательством срабатывания, его нужно проверить шагом 4. Если обновление цены делается внешним импортом напрямую в таблицу БД, событие может не прийти; фоновая сверка устраняет это с задержкой.

## 4. Cron — включать после теста событий

Сначала посмотреть существующие задания: `crontab -l`. Через `EDITOR=vi crontab -e` добавить **одну** строку в crontab пользователя `als`:

```cron
* * * * * /opt/remi/php74/root/usr/bin/php /var/www/discount-tools/tools/dt_catalog_sort_auto.php --run --queue=100 --sweep=300 --apply --confirm=test >> /home/als/dt_catalog_sort_auto.log 2>&1
```

Каждый запуск защищён `flock`; при ещё работающем предыдущем worker следующий завершится с сообщением о блокировке. На текущей конфигурации сначала замерить время исполнения и нагрузку тестового сервера. При необходимости уменьшить `--sweep=300`.

Проверять `tail -n 30 /home/als/dt_catalog_sort_auto.log`, `$PHP "$TOOL" --status`, и актуальность карточки после обновления цен.

## 5. Проверка скидок и сроков их действия

`GetOptimalPrice()` считает текущую итоговую цену для **анонимной группы 2, s1, RUB, без купонов**. Скидки для других групп покупателей и персональные купоны могут давать иные цены; индекс для них не обещает точного совпадения.

При смене скидки (в каталоге или маркетинге) события перезапускают полный проход. Также каждый worker непрерывно обходит каталог независимо от событий: так новые/истёкшие скидки будут применяться при следующей сверке соответствующего ID. Для гарантий обновления точно к минуте окончания акции потребуется дополнительная очередь времени переходов — пока не реализована.

## 6. Откат

1. Удалить **только добавленные строки** V4 из `local/php_interface/init.php` (в VSCode); синтаксис `php -l`.
2. Убрать **только запись cron V4** (`EDITOR=vi crontab -e`).
3. При необходимости удалить новые файлы V4 после резервной копии. **Не удалять** старый `dt_catalog_sort.php`, `section.php` и свойства V3.
4. Таблицы V4 можно оставить для исследования; удалять их отдельно только по утверждённому плану после резервной копии БД. Старые значения сортировки продолжат отображаться, но перестанут обновляться автоматически.

## Ограничения до production

- Подтвердить событие изменения цены на текущем Битрикс, в том числе при импорте.
- Проверить изменение скидки, окончание срока акции и поведение композитного кеша.
- Проверить точность SKU, если в инфоблоке 17 снова появятся активные предложения.
- Убедиться в приемлемой нагрузке полного прохода 6074 товаров и отсутствия повторов на границах страниц.
- Перенос на production потребует адаптации запрета hostname, резервного копирования, миграции таблиц, развёртывания и настройки отдельных прав, **не делается этим тестовым пакетом**.


## V4.2: исправление `--sweep=0`

В V4.1 `--run --sweep=0` мог обработать один элемент и переместить курсор, потому что `nTopCount=0` не гарантирует пустую выборку в используемой версии Битрикс. V4.2 явно прекращает sweep, если лимит равен 0. Если CLI и библиотека V4.1 уже размещены, замените **только** `/local/php_interface/dt_catalog_sort/DtCatalogSortAuto.php` на библиотеку из этого пакета. `section.php`, свойства, таблицы и CLI изменять не нужно.

Контроль: до и после запуска `$PHP "$TOOL" --run --queue=0 --sweep=0 --apply --confirm=test` значение `sweep_cursor` должно совпадать, а статистика должна содержать `SWEEP {"selected":0,"changed":0,"failed":0,...}`. События `init.php` и cron подключайте только после этой проверки.

Следующий шаг: сделайте резервную копию `local/php_interface/init.php` вне public; добавьте **только PHP-операторы** из `deploy/init.snippet.php` внутри существующего PHP-блока, не вставляя второй `<?` в уже открытый блок; проверьте `php -l`. Сохраните исходную кодировку файла. Затем через админку измените цену одного тестового товара, проверьте `--status`, и лишь после появления очереди запускайте `--run --queue=20 --sweep=0 --apply --confirm=test`.
