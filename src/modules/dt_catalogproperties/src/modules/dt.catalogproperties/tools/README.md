# Автоматическое назначение характеристик категорий (инфоблок 16)

`auto_fill_section_properties.py` — отдельная CLI-утилита. Работает напрямую с MySQL через системную команду `mysql`; ядро 1С-Битрикс не загружает. Требуются `python3` (3.6+) и mysql-client. Проверено на VM 247: сначала отдельная категория №1828, затем весь инфоблок №16 (`--dry-run` и `--apply`).

## Правила

- Категории обходятся по дереву `LEFT_MARGIN`. Уже настроенные (`dt_cp_section_config`) **не изменяются**, даже если набор пуст.
- Для **ненастроенной** категории итоговый список = текущий набор непосредственно родительской категории (в том числе рассчитанный для родителя в этом же проходе); если родительского набора нет, сначала вставляется фиксированный базовый список из 8 свойств `338, 88, 121, 516, 94, 89, 522, 523`. Затем добавляются новые технические свойства `PROP[0-9]+`, которые **хотя бы у одного товара, напрямую привязанного к разделу, имеют непустое значение**.
- Привязки учитываются как по `b_iblock_section_element`, так и по `b_iblock_element.IBLOCK_SECTION_ID`; дубли исключаются.
- Товары в **подразделах не считаются товарами самого родителя**. При отсутствии наследуемого набора верхний раздел получает 8 базовых полей даже без собственных товаров. Уже настроенные родительские и дочерние наборы не перезаписываются.
- Для настроенного родителя его фактический набор используется без изменений, независимо от того, активны ли все свойства сейчас. Новые обнаруженные свойства — только активные технические `PROP...`.
- Важный нюанс: данные товаров в Bitrix могут храниться в `b_iblock_element_property` (VERSION=1) или `b_iblock_element_property_s16` + `_m16` (VERSION=2); обе схемы поддерживаются. Пустые строки/NULL не учитываются, число `0` считается заполненным.
- Порядок: свойства родителя как есть; новые собственные — по возрастанию ID. В созданных наборах порядок записывается как 100, 200, ... .
- Пустые итоговые наборы **пропускаются** и остаются ненастроенными (в отличие от ручного создания явно пустой конфигурации).
- Скрипт не изменяет файлы, свойства продуктов, структуру инфоблоков или кеш CMS.

## Порядок запуска на VM 247

Файл разместить по пути:
`/var/www/discount-tools/public/local/modules/dt.catalogproperties/tools/auto_fill_section_properties.py`.

Проверить установленный MySQL-клиент: `sudo mysql --version`. Подключение по умолчанию — `sudo mysql kanuk_utf8`. Пароль MySQL в Git **не записывать**. Если доступ через отдельную учётную запись — используйте `--mysql 'mysql --defaults-extra-file=/protected/mysql-client.cnf'`, установив права `0600` на файл вне сайта.

Сначала сделать резервную копию **обеих** таблиц конфигурации, пример для VM 247 (выполнять в безопасном каталоге вне docroot):

```bash
sudo mysqldump --single-transaction kanuk_utf8 \
  dt_cp_section_config dt_cp_section_property \
  > /home/als/dt_cp_before_autofill.sql
chmod 600 /home/als/dt_cp_before_autofill.sql
```

Если shell не может записать этот файл, запускайте команду под пользователем с доступом к каталогу. Не добавляйте SQL-дамп в Git.

Для проверки всего дерева:

```bash
python3 /var/www/discount-tools/public/local/modules/dt.catalogproperties/tools/auto_fill_section_properties.py \
  --dry-run --database kanuk_utf8 \
  --output-dir /home/als/dt_cp_autofill_report
```

Для проверки отдельной ветки, например «Ручной инструмент»:

```bash
python3 /var/www/discount-tools/public/local/modules/dt.catalogproperties/tools/auto_fill_section_properties.py \
  --dry-run --section-id 1583 --output-dir /home/als/dt_cp_autofill_1583
```

В каталоге отчёта появятся:

- `sections.csv`: сколько у раздела непосредственно связанных товаров, унаследованных, базовых и новых свойств;
- `properties.csv`: полный список свойств для каждой создаваемой конфигурации, откуда пришло свойство (`PARENT`/`BASE`/`PRODUCT`), итоговая сортировка;
- `plan.json` и `plan.sha256`: полное предложение и его SHA-256.

Проверьте крупные списки, сомнительные свойства, пустые корневые категории и настройки вручную созданных верхних уровней. **По умолчанию используется исключительно `--dry-run`.**

Запись разрешена только после анализа отчёта. Для всего каталога (значение хеша из `plan.sha256`):

```bash
HASH=$(cat /home/als/dt_cp_autofill_report/plan.sha256)
python3 /var/www/discount-tools/public/local/modules/dt.catalogproperties/tools/auto_fill_section_properties.py \
  --apply --database kanuk_utf8 \
  --output-dir /home/als/dt_cp_autofill_report \
  --confirm APPLY_SECTION_CONFIG_16 \
  --expected-sha256 "$HASH"
```

При запуске `--apply` скрипт **повторно считывает базу и строит план**. Если он отличается от просмотренного, операция отменяется. Конфигурации добавляются в одной транзакции, существующие категории защищены `INSERT IGNORE` плюс `ROW_COUNT()`. Новый файл `apply.sql` сохраняет SQL применённого плана (вне docroot) для аудита.

После записи проверить выборочно новые категории в админке и витрине. Массовая запись SQL в обход `SectionRules` **не вызывает** адресную очистку composite-кеша. При активном composite-кеше для проверки обновлённых карточек потребуется отдельно выполнить безопасную адресную инвалидацию/плановую очистку после анализа количества URL; глобальную очистку модуль не запускает.

Не запускайте на production без отдельного бэкапа и проверки домена, БД, таблиц и схемы свойств. Скрипт рассчитан на существующие ID инфоблока 16.

## Базовый набор для разделов без наследуемых характеристик

Порядок фиксирован и соответствует набору на скриншоте: `Модель (338)`, `Описание (88)`, `Тип (121)`, `Габариты с упаковкой (516)`, `Габариты, мм (94)`, `Вес, кг (89)`, `Вес нетто, кг (522)`, `Вес брутто, кг (523)`. Скрипт проверяет их наличие и активность; если свойства отсутствуют, завершается с ошибкой до записи. Затем добавляет заполненные свойства непосредственно привязанных товаров по ID, без повторов. Для категории №1828 фактически выполнены `--dry-run` и `--apply`: 8 базовых + 9 новых = 17 характеристик; результат проверен SQL и в админке VM 247.
