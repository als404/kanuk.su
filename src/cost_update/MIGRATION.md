# Восстановление `cost_update` после переноса на `discount-tools.ru`

**Назначение:** автоматическая синхронизация цен и остатков из Google Sheets и ручной CSV-импорт через интерфейс сайта.

- **Автоматически:** бренды, перечисленные в `config.php` (сейчас BREXIT и ESSON).
- **Вручную:** любой активный бренд из инфоблока 14; файл CSV содержит `артикул;стоимость;количество`.
- **Среда тестирования:** PHP 7.4, MySQL UTF-8, инфоблок товаров 16.

> Переносится сайт вместе с тестовой БД UTF-8. Отдельная конвертация базы из CP1251 не требуется. Команды ниже выполнять на новом сервере, подставляя **реальный** путь к сайту и исполняемому PHP.

## 1. Проверить файлы и конфигурацию

Убедиться, что перенесён каталог:

```text
<корень_сайта>/local/modules/cost_update/
```

Открыть в VS Code файл:

```text
local/modules/cost_update/config.php
```

Проверить основные параметры:

```php
'document_root'       => dirname(__DIR__, 3),
'site_id'             => 's1',
'iblock_id'           => 16,
'article_property_id' => 51,
'brand_facet_id'      => 104,
'brands_iblock_id'    => 14,
'price_group_id'      => 1,
'html_cache_domain'   => 'discount-tools.ru',
'catalog_path'        => '/catalog/',
```

`document_root` можно оставить с `dirname(__DIR__, 3)`, если структура папок не изменилась. `brand_facet_id = 104` — **ID фасета** таблицы `b_iblock_16_index`, не ID свойства из `b_iblock_property`.

При изменении основного домена заменить `html_cache_domain` на фактический домен HTML-кэша Битрикс. Проверить, что кеш действительно размещается в `bitrix/html_pages/discount-tools.ru/`.

## 2. Где менять Google Spreadsheet ID и GID листов

**Все настройки находятся в том же `local/modules/cost_update/config.php`.**

```php
'spreadsheet_id' => 'ID_ВАШЕЙ_GOOGLE_ТАБЛИЦЫ',
'brands' => [
    'BREXIT' => [
        'code'          => 'brexit',
        'gid'           => 'GID_ЛИСТА_BREXIT',
        'range'         => 'C:AW',
        'article_index' => 0,
        'price_index'   => 45,
        'stock_index'   => 46,
    ],
    'ESSON' => [
        'code'          => 'esson',
        'gid'           => 'GID_ЛИСТА_ESSON',
        'range'         => 'C:M',
        'article_index' => 0,
        'price_index'   => 9,
        'stock_index'   => 10,
    ],
],
```

**Как найти значения в ссылке Google Sheets:**

```text
https://docs.google.com/spreadsheets/d/1ABCdef012345XYZ/edit#gid=123456789
                                    └───────┬───────┘         └───┬───┘
                                       spreadsheet_id             gid
```

- `spreadsheet_id` — часть адреса **между `/d/` и `/edit`**. Общий для всей книги.
- `gid` — числовой идентификатор **конкретного листа** после `gid=`. У каждого листа свой.
- `code` — символьный код соответствующего активного бренда в инфоблоке 14; он должен совпадать с фактическим `CODE`.
- `range` — диапазон столбцов, выгружаемых из Google Sheets. Индексы `article_index`, `price_index`, `stock_index` отсчитываются **от первого столбца диапазона с нуля**, а не от столбца A.

Текущие соответствия:

| Бренд | Артикул | Цена | Остаток | Диапазон | Индексы (артикул / цена / остаток) |
|---|---|---|---|---|---|
| BREXIT | C | AV | AW | `C:AW` | `0 / 45 / 46` |
| ESSON | C | L | M | `C:M` | `0 / 9 / 10` |

Для BREXIT используется остаток из `AW` (склад Канюк); `AX` не участвует.

**Важно:** после переноса проверить доступность Google CSV-экспорта с нового сервера и то, что выбранные `spreadsheet_id`/`gid` относятся к **нужной**, а не временной тестовой книге. Не запускать `--apply`, пока DRY-RUN не подтвердил ожидаемые изменения.

## 3. Как добавить новый бренд

### 3.1. Только для ручного CSV

**Ничего в `config.php` добавлять не нужно.** Форма `index.php` автоматически получает все активные бренды из инфоблока 14. Если бренд создан там, активен и привязан к товарам через фасетный индекс, он появится в списке.

Порядок проверки: открыть форму → выбрать бренд → загрузить CSV → выполнить DRY-RUN → сверить найденные товары → только затем включить запись в MySQL.

### 3.2. Для автоматической синхронизации Google Sheets

В `config.php` добавить новый элемент в массив `'brands'`:

```php
'NEW_BRAND' => [
    'code'          => 'new-brand', // фактический CODE бренда в инфоблоке 14
    'gid'           => '123456789', // gid листа в Google Sheets
    'range'         => 'C:M',       // реальный диапазон столбцов
    'article_index' => 0,           // C
    'price_index'   => 9,           // L
    'stock_index'   => 10,          // M
],
```

Это **пример**, а не готовые значения для произвольного бренда. Перед включением:

1. Убедиться, что бренд существует в инфоблоке 14, активен и его `CODE` совпадает с `'code'`.
2. Определить реальные столбцы артикула, цены и остатков на новом листе; настроить `range` и индексы с нуля.
3. Проверить `gid` листа и доступ к CSV-экспорту.
4. Выполнить `cron.php` **без `--apply`** и проверить в журнале строки `Parsed NEW_BRAND` и `DRY-RUN NEW_BRAND`.
5. Проверить число `missing`, `ambiguous`, `price`, `stock`. При неожиданных массовых изменениях **не запускать запись**.
6. Только после проверки выполнить `--apply` и проверить пару товаров на сайте.

> Добавление записи в массив `brands` автоматически включает бренд в **каждый** запуск cron. Отдельное cron-задание для нового бренда не требуется. Текущая реализация использует **один `spreadsheet_id` на все бренды**; если новый бренд находится в другой книге, одного `gid` недостаточно — потребуется доработка загрузчика.

## 4. Проверить права доступа

PHP-FPM и cron должны иметь права на чтение кода и запись в:

```text
local/modules/cost_update/runtime/
```

Особенно проверить `sync.lock`, `sync.log`, `cron.log`, `pending_cache.json` и файлы Google-кеша. Ранее проблема `Another synchronization is running` была вызвана файлом `sync.lock`, принадлежавшим `root`.

На новом хостинге назначить владельцем рабочего каталога и его файлов **пользователя сайта** (имя может отличаться от `kanuk`). Не запускать cron от `root`, если он создаёт файлы, недоступные PHP-FPM. Файлы журнала и очереди не должны быть доступны через HTTP: проверить правила запрета доступа к `/local/modules/cost_update/runtime/` в Nginx.

## 5. Настроить cron

Создать **одно** задание от пользователя сайта; команда:

```bash
cd /ПУТЬ_К_САЙТУ && /ПУТЬ_К_PHP74/php local/modules/cost_update/cron.php --apply >> local/modules/cost_update/runtime/cron.log 2>&1
```

Запуск **каждый час с 07:00 до 22:00 включительно**:

```cron
0 7-22 * * *
```

Расписание трактуется в часовом поясе сервера. Если cron работает по UTC, а нужны **07:00–22:00 по Москве (UTC+3)**:

```cron
0 4-19 * * *
```

## 6. Проверка после переноса

Из корня сайта выполнить **сначала проверку без записи**:

```bash
/ПУТЬ_К_PHP74/php local/modules/cost_update/cron.php
```

Затем, если данные и количества изменений ожидаемы:

```bash
/ПУТЬ_К_PHP74/php local/modules/cost_update/cron.php --apply
```

Проверить журналы:

```bash
tail -n 30 local/modules/cost_update/runtime/sync.log
tail -n 30 local/modules/cost_update/runtime/cron.log
```

Успешный запуск содержит `Parsed ...` и `UPDATED ...` по настроенным брендам. `price:0` и `stock:0` — нормальная ситуация, если данные актуальны. Убедиться, что нет `Permission denied`, ошибок доступа к Google и незавершённой очереди очистки кеша.

**Ручной импорт:** открыть под администратором:

```text
https://discount-tools.ru/local/modules/cost_update/index.php
```

Загрузить CSV (`артикул;стоимость;количество`), проверить DRY-RUN, затем контролируемую запись и отображение товара. Пустое поле не меняет значение; `0` в количестве при включённом обновлении остатков означает отсутствие товара. Убедиться, что неавторизованный пользователь не получает доступ к форме.

**Завершение:** дождаться первого запуска именно по расписанию cron и проверить время и отсутствие ошибок в `cron.log`.
